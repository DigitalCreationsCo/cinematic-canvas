## Deep Dive: Advanced Component Mocking Using The Decoupled Singleton Pattern

Testing stateful, asynchronous pipelines like our generative worker queues often requires control mechanisms over internal dependencies. Standard inline mocking often degrades into verbose, fragile implementations and initialization errors.

We solved these issues with a **Decoupled Singleton Mock** pattern. By externalizing the mock instance and binding it to an eagerly-imported singleton, we decouple module resolution and bridge the scope of the test suite with the scope of the component module.

### Why this architecture wins:

1. **Identity Stability:** JavaScript object equality is determined by memory reference. By overriding constructors to return a static singleton, the application and the test suite interact with the exact same memory address. Mutations propagate instantly.
2. **Hoisting Compliance:** Vitest hoists `vi.mock` declarations to the top of the file. Attempting to pass external variables into a mock factory typically triggers a `ReferenceError` (the Temporal Dead Zone). By wrapping the singleton instantiation in `vi.hoisted`, the testing engine allocates the mock object at the absolute beginning of the execution lifecycle.
3. **Zero-Overhead Control:** The test suite imports pre-configured spies directly, eliminating the need to constantly cast imported functions.

### Use Cases

* **Stateful Services:** Classes handling database polling or task claiming.
* **External API Wrappers:** Encapsulating LLM or media generation APIs to simulate timeouts or rate limits.
* **Event Emitters:** Allowing the test suite to inspect emitted events and trigger synthetic incoming events from the same instance.

### Implementation Pattern

#### 1. Mock Definition (`mock-job-control-plane.ts`)

```typescript
// Initialize the singleton before imports are resolved
const { _mockJobControlPlane } = await vi.hoisted(async () => {
  const { createMockJob } = await import("#shared/mocks/mock-jobs.ts");
  const { generateId } = await import("#shared/utils/id.ts");
  
  const _createMockJobControlPlane = () => ({
    createJob: vi.fn().mockResolvedValue(createMockJob()),
    claimJob: vi.fn(),
    updateJob: vi.fn(),
    jobId: vi.fn().mockReturnValue(generateId()),
    // ... additional spies
  });
  
  return { _mockJobControlPlane: _createMockJobControlPlane() };
});

// Intercept the module resolution
vi.mock("#shared/services/job-control-plane.ts", () => ({
  JobControlPlane: class {
    constructor() {
      return _mockJobControlPlane;
    }
  },
}));

```

#### 2. The Execution (`worker-service.test.ts`)

```typescript
import { mockJobControlPlane } from "#shared/mocks/mock-job-control-plane.ts";
import { WorkerService } from "#worker/worker-service.js";

describe("WorkerService", () => {
  beforeEach(() => vi.clearAllMocks());

  it("processes claimed jobs", async () => {
    mockJobControlPlane.claimJob.mockResolvedValue({ id: "job-01", status: "pending" });
    
    const service = new WorkerService(); 
    await service.processNext();

    expect(mockJobControlPlane.claimJob).toHaveBeenCalled();
    expect(mockJobControlPlane.updateJob).toHaveBeenCalledWith("job-01", "processing");
  });
});

```

## Test Infrastructure & Memory Management

The Cinematic Canvas test suite was silently accumulating a critical memory leak. **Zustand's temporal middleware**—which powers our undo/redo system—maintains a rolling history of snapshots. Our previous mocking strategy allowed these snapshots to persist across test boundaries, eventually exhausting the JavaScript heap.

* **The Fix:** `mock-store.ts` was rewritten to create completely isolated mock stores—no temporal middleware, no undo history, no cross-test state leakage.
* **Workspace Configs:** A new `vitest.workspace.ts` splits the suite into two process models: `vmForks` for client tests (React) and `forks` for backend tests (Node.js).
* **Prompt Test Expansion:** 9 new test files covering character specs and cinematography bring total prompt coverage to **105 passing tests**.
